## 4. Verified non-issues (looked wrong / was probed, is correct)

1. **`createFunction` trampoline & exception safety — no defect exists in this tree.** The review brief flagged a "std::function trampoline"; the current code has none. `createFunction` (`Database.cpp:178-196`) forwards raw C function pointers (`apFunc`/`apStep`/`apFinal`/`apDestroy`) and `apApp` verbatim to `sqlite3_create_function_v2`. There is no captured `std::function`, no wrapper-owned state, hence no lifetime or exception-crossing risk *added by the wrapper*: if a user's C callback throws, that is the user's C-boundary violation, identical to using the C API directly. `SQLITE_UTF8 | SQLITE_DETERMINISTIC` composition and the `0x800` fallback define (`Database.cpp:22-24`) match sqlite3.h.
2. **No `apApp` leak on registration failure.** `sqlite3_create_function_v2` documents that `xDestroy` is invoked on the app pointer **even when registration fails**; the wrapper's `check(ret)` throw after failure is therefore leak-free without extra handling.
3. **Constructor error path is leak/UAF-free.** `Database.cpp:69-75`: the (possibly non-null) failed handle is `reset()` into `mSQLitePtr` *before* the throw, so unwinding closes it exactly once; `Exception(handle, ret)` reads `sqlite3_errmsg` while the handle is still open; the OOM case (`handle == nullptr`) is defined (`sqlite3_errmsg(NULL)` returns static "out of memory"). If `setBusyTimeout` throws (line 78), the already-owned handle is likewise closed by unwinding.
4. **`sqlite3_close(nullptr)` in the Deleter is a documented harmless no-op** — moved-from `Database` destruction is safe (exercised by the `moveConstructor` test).
5. **`tryExec(nullptr)` is safe and `noexcept` is honest.** `sqlite3_exec` substitutes `""` for a NULL SQL pointer (legacy.c) and the wrapper allocates nothing on that path.
6. **`std::filesystem::path` ctor has no dangling temporary.** `apFilename.u8string().c_str()` (`Database.h:242`) — the temporary string outlives the delegated-constructor call (end of full-expression); the `reinterpret_cast` from `const char8_t*` under C++20 is valid.
7. **`getHeaderInfo` buffer bounds are correct.** The 100-byte read is length-checked (`gcount() < 100` throws) before parsing; the highest access is `readBE32(96)` → `buf[99]`, in bounds; every `Header` field is assigned before return on the success path.
8. **`isUnencrypted` post-#553 cannot read uninitialized memory**: `char header[16] = {}` plus C++11 `read()` semantics (writes only extracted chars) means the `memcmp` always sees defined bytes even on short files.
9. **`key("")` behavior without codec is intentional**: silent no-op (passLen guard, `Database.cpp:237`) matching the codec build's no-op, verified by the non-codec `encryptAndDecrypt` test (`EXPECT_NO_THROW(db.key(""))`).
10. **`loadExtension` enable/disable ordering is sound** (re-verified against SQLITE_DBCONFIG docs): per-connection `SQLITE_DBCONFIG_ENABLE_LOAD_EXTENSION` keeps SQL `load_extension()` disabled (C-API-only enablement); variadic `NULL` instead of `nullptr` is deliberate and portable. It never re-disables afterwards, but the enable is connection-scoped and the security note documents the trade-off. Only the DB-06 diagnostics gap remains.
11. **`rekey("")` decrypt path** (`Database.cpp:256`, codec build): `sqlite3_rekey(handle, nullptr, 0)` is the documented decrypt idiom for SEE/SQLCipher-style codecs — correct.
12. **Busy-timeout handling is correct**: ctor applies it only when `> 0` (`Database.cpp:76-79`); `sqlite3_busy_timeout(handle, <=0)` clears the handler, so skipping it changes nothing; `setBusyTimeout` is a thin checked wrapper. Round-trips verified by the `busyTimeout` test via `PRAGMA busy_timeout`.
