## 1. Fix verification (SP-02, SP-03, TXN-08)

### SP-03 — Savepoint destructor `catch(...)` — **VERIFIED COMPLETE**
`src/Savepoint.cpp:49` now reads `catch (...)`. The `try` block at `:41-48` encloses the whole destructor body, including the `std::string("ROLLBACK TO SAVEPOINT ") + msName` / `RELEASE` string constructions performed inside `rollbackTo()`/`release()` (`:62`, `:76`), so `std::bad_alloc` and any non-`SQLite::Exception` are contained. The new regression test `tests/Savepoint_test.cpp:133-148` (`destructorSwallowsException`) forces the destructor's commands to fail and asserts no escape. Complete.

### TXN-08 — Transaction destructor `catch(...)` — **VERIFIED COMPLETE**
`src/Transaction.cpp:58` now reads `catch (...)`. Placement covers ALL statements in the destructor: the only statement is `mDatabase.exec("ROLLBACK TRANSACTION")` at `:56`, inside the `try` at `:54-61`. No `std::string` is built outside the `try` — `Database::exec(const char*)` (`include/SQLiteCpp/Database.h:307`) is selected for the literal, so there is no temporary construction before entering the guarded region either. `CHANGELOG.md` entry present. Complete.

### SP-02 — `mbRolledBack` state flag — **FIX LANDED, BUT INTRODUCES A REGRESSION (see SP-09)**
The flag exists (`include/SQLiteCpp/Savepoint.h:96`), is set by `rollbackTo()` (`src/Savepoint.cpp:77`), and the destructor consults it (`:43-46`) to issue a single `RELEASE` when a rollback already happened. The new test `rollbackToThenRelease` (`tests/Savepoint_test.cpp:108-131`) covers manual `rollbackTo()` → `release()`. Interactions checked:
- `mbRolledBack` + `release()`: `release()` does not (and need not) reset `mbRolledBack`; after `release()`, `mbReleased == true` makes the destructor a no-op regardless of `mbRolledBack`. Correct.
- Rollback-succeeded-but-release-failed case: if `rollbackTo()` succeeds in the destructor but `release()` throws (e.g. savepoint released behind the object's back, as in the `destructorSwallowsException` test, or transient error), the exception is swallowed by `catch(...)` and the savepoint can remain on the connection's stack until an outer release/commit. This residual leak is inherent to a non-throwing destructor and has **no diagnostic** — it is the Savepoint side of still-open TXN-01 / ranked fix #10 (`SQLITECPP_ASSERT` routing), not a new defect. Acceptable as-is once fix #10 lands.
- Rollback-failed case: if `rollbackTo()` throws in the destructor, `release()` is never attempted (single `try` block). When the savepoint no longer exists this is correct; when the failure is transient (BUSY) the release is skipped too — same observability gap, same remedy (fix #10).
- **However**, the `if (!mbRolledBack)` skip changes documented semantics for work performed *after* a manual `rollbackTo()` — a genuine behavioral regression, filed as **SP-09** below with empirical evidence.

| [ ] | SP-09 | High | High | bug (regression, afa51d3) | `src/Savepoint.cpp:43-46`; contract at `include/SQLiteCpp/Savepoint.h:30-32`, `:76` | Work written **after** a manual `rollbackTo()` is silently **committed** on scope exit instead of rolled back, violating the documented "rolled back in the destructor (unless committed before)" guarantee. ## 4. Verified non-issues (evidence-based)

1. **`quote()` produces a string literal, not an identifier — and that is valid savepoint SQL.** `SELECT quote('sp')` returns `'sp'` (single-quoted string literal). SQLite's grammar accepts a string literal wherever a savepoint name (`nm`) is expected: empirically, `SAVEPOINT 'sp x'`, `ROLLBACK TO SAVEPOINT 'sp x'`, `RELEASE SAVEPOINT 'sp x'` all succeed, including names containing embedded quotes (`SAVEPOINT '''sp'''` / `RELEASE SAVEPOINT '''sp'''` round-trip OK). The literal's *value* is the savepoint name, so a savepoint created as `SAVEPOINT 'sp'` matches `RELEASE SAVEPOINT sp` and vice-versa (the `destructorSwallowsException` test at `tests/Savepoint_test.cpp:146` exploits exactly this). No SQL-validity bug; the quoting scheme is sound for all inputs except the known NUL truncation (SP-04).
2. **Empty savepoint name is legal.** `quote('')` returns `''`, and `SAVEPOINT ''` / `RELEASE SAVEPOINT ''` both execute successfully (verified). A `Savepoint(db, "")` therefore works end-to-end; no guard needed.
3. **Repeated `ROLLBACK TO` on the same savepoint is harmless.** Verified: `ROLLBACK TO` leaves the savepoint on the stack and a second `ROLLBACK TO` succeeds, discarding any intervening writes. This is what makes the SP-09 proposed fix (unconditional destructor rollback) safe, and what the pre-afa51d3 destructor and `tests/Savepoint_test.cpp:80-93` (`sp4`) rely on.
4. **`TransactionBehavior` enum vs switch is exhaustive and safe.** The three enumerators (`include/SQLiteCpp/Transaction.h:26-30`) are each handled in `src/Transaction.cpp:26-38`; `stmt` cannot be read uninitialized (every non-throwing path assigns it); the `default:` throws before `exec`, so a throwing constructor never leaves a transaction open. The only residual concern is compile-time exhaustiveness (TXN-02, unchanged).
5. **TXN-08 `catch(...)` scope is complete.** No statement of `~Transaction()` sits outside the `try` (see §1); there is no equivalent of Savepoint's string concatenation because the SQL is a `const char*` literal dispatched to `Database::exec(const char*)`.
6. **`~Transaction()` / `~Savepoint()` against a destroyed or moved-from `Database` is UB that `catch(...)` cannot mask — but it is not a new finding.** Both destructors dereference a `Database&`; if the `Database` was destructed or moved-from first, `exec()` runs on a dangling object / null handle, which is undefined behavior (a crash, not an exception). This is exactly TXN-06 (documented lifetime contract) plus DB-12 (defaulted `Database` move); no additional ID warranted. Note only that the new `catch(...)` should not be mistaken for protection here.
7. **`mbRolledBack` vs `release()` bookkeeping is internally consistent.** `release()` after `rollbackTo()` works (savepoint still on stack — verified, and covered by `tests/Savepoint_test.cpp:108-131`); after `release()`, both `rollbackTo()` and `release()` correctly throw "Savepoint already released." (`src/Savepoint.cpp:67`, `:81`), and the destructor is a no-op. The only flaw in the state machine is the destructor skip (SP-09).
8. **Test knowledge-coupling in `destructorSwallowsException` is acceptable.** `tests/Savepoint_test.cpp:146` hardcodes the internal quoted form (`RELEASE SAVEPOINT 'sp'`); as shown in item 1, the bare identifier would match the same savepoint anyway, so the test is not actually brittle to the quoting scheme.
